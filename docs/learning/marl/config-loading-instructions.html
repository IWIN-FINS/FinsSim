FinsSim MARL 配置读取流程 Instruction

这份文档只描述一件事：当你使用顶层 FinsSim 命令启动 MARL 训练时，配置是如何从 configs/marl/*.yaml 一层层读取并传递到最终训练脚本里的。

1. 先建立一个正确心智模型

  • configs/marl/*.yaml 是顶层实验入口配置。
  • base_config 表示后端内部的 Python 配置名称。
  • 顶层 YAML 负责统一实验元信息、Unity 运行参数、以及后端 CLI 覆盖参数。
  • 具体 MARL 场景参数、算法工厂方法、训练默认值，定义在 python/finssim_marl/src/finssim_marl/training/ 下的 Python 配置模块中。

2. 训练命令入口

典型入口命令：

uv run --package finssim-cli finssim marl train -c configs/marl/3chase1/end_to_end.yaml

这个命令的控制流分成两层：

  1. 顶层统一入口 finssim-cli 读取 YAML。
  2. 再把解析后的参数转成 MARL 后端命令，交给 finssim-marl 执行。

3. 顶层 YAML 如何被读取

Step 1: CLI 进入统一后端调度逻辑

MARL 训练命令会进入 finssim_cli.main._run_backend()。

python/finssim_cli/src/finssim_cli/main.py

Step 2: 读取 experiment YAML

_run_backend() 调用 load_experiment_config(config) 读取文件。

python/finssim_core/src/finssim_core/config_loader.py

Step 3: YAML 被解析成统一数据结构

load_experiment_config() 用 yaml.safe_load() 读取 YAML， 然后组装成 FinsSimExperimentConfig。

python/finssim_core/src/finssim_core/config_loader.py
YAML 字段 读取后进入哪里
base_config FinsSimExperimentConfig.base_config
experiment ExperimentConfig
unity UnityRuntimeConfig
trainer TrainerConfig

4. 顶层 YAML 里的四块配置分别做什么

块 职责
base_config 选择 MARL 后端中的哪一个 Python 场景配置对象。
experiment 定义实验名、seed、tags 等公共元信息。
unity 定义 Unity 运行时参数，比如 env_path、num_envs、env_base_port、time_scale。
trainer 定义后端类型和额外覆盖参数，其中 trainer.overrides 会被原样转发到后端 CLI。

5. 顶层 CLI 如何把 YAML 转成后端命令

顶层入口不会自己训练。它的工作是把统一配置翻译成一个实际可执行的 MARL 后端命令。

Step 4: 生成 backend command

finssim_cli.main._build_backend_command() 负责把统一配置转成命令行参数。

python/finssim_cli/src/finssim_cli/main.py

关键映射关系：

统一配置字段 后端 CLI 参数
base_config --config
experiment.name --exp-name
unity.env_base_port --env-base-port
unity.time_scale --time-scale
unity.num_envs --num-envs
unity.env_path --env-path
unity.no_graphics 若为 false，则追加 --show-graphics
trainer.overrides 追加为额外 CLI 参数，例如 total_timesteps、device、overwrite

6. MARL 后端如何继续读取配置

Step 5: 进入 finssim-marl

顶层 CLI 最终会执行类似下面的命令： 

uv run finssim-marl train --config <base_config> --exp-name <experiment.name> ...
python/finssim_marl/src/finssim_marl/cli.py

Step 6: CLI wrapper 转发到真正训练脚本

finssim_marl/cli.py 根据子命令把执行转给 scripts/train.py。

python/finssim_marl/scripts/train.py

Step 7: 训练脚本先解析 CLI 参数

scripts/train.py 使用 tyro.cli(TrainArgs) 读取后端命令行参数。

python/finssim_marl/scripts/train.py

7. base_config 在 MARL 后端里如何解析

Step 8: 用 get_config(config_name) 查 Python 配置对象

训练脚本执行： 

base_config = get_config(args.config)
config = base_config.create_train_config()
python/finssim_marl/scripts/train.py

Step 9: get_config() 从注册表取出 BaseConfig 对象

get_config() 定义在 training/config.py，从内部字典 _CONFIGS_DICT 中按名称查找。

python/finssim_marl/src/finssim_marl/training/config.py

Step 10: 注册表来自各场景配置模块

当前 MARL 配置注册表通过 get_chasing_configs() 收集场景配置对象， 再放进 _CONFIGS 和 _CONFIGS_DICT。

python/finssim_marl/src/finssim_marl/training/config.py
python/finssim_marl/src/finssim_marl/training/chasing_3_chase_1_config.py

8. Python 场景配置对象如何变成最终 TrainConfig

Step 11: BaseConfig 是场景级配置抽象

BaseConfig 里既有通用训练字段，也定义了几个工厂方法，比如：

  • create_train_config()
  • create_mappo_config()
  • create_algorithm()
  • create_rollout_buffer()
python/finssim_marl/src/finssim_marl/training/config.py

Step 12: 场景子类展开为 TrainConfig

例如 Chasing3Chase1Config.create_train_config() 会把：

  • 场景配置对象本身的字段
  • env_config 中的环境参数
  • training_config 中的训练参数

合并后展开成训练脚本真正使用的 TrainConfig。

python/finssim_marl/src/finssim_marl/training/chasing_3_chase_1_config.py

这一步之后，训练脚本拿到的是一个扁平的训练配置对象，而不是嵌套 YAML 结构。

9. CLI 覆盖参数何时生效

在 base_config.create_train_config() 生成默认 TrainConfig 之后， 训练脚本还会调用 merge_cli_args()，把后端命令行参数覆盖到最终配置上。

因此优先级可以这样理解：

TrainConfig 默认值
  < Python BaseConfig / env_config / training_config
  < 顶层 FinsSim YAML 映射成的后端 CLI 参数
  < trainer.overrides 追加的后端 CLI 覆盖参数
python/finssim_marl/scripts/train.py

10. 如何从 YAML 传入后端参数

如果你想传入类似 --overwrite、--num-eval-envs=1 这样的后端参数， 应该写在 trainer.overrides 下。 

trainer:
  backend: marl
  overrides:
    overwrite: true
    num_eval_envs: 1

顶层 CLI 会把它们转换成后端命令行参数：

--overwrite --num-eval-envs 1

转换规则：

  • snake_case key 会转成 --kebab-case 参数。
  • 布尔值 true 会转成单独 flag，例如 overwrite: true 会变成 --overwrite。
  • 数值和字符串会变成 --flag value 形式。
  • 列表会展开成一个 flag 后接多个值。

限制也很明确：只有后端 CLI 自己声明过的参数，才能这样透传。对于 MARL， 这些参数首先要存在于 TrainArgs 中，后续还要被 merge_cli_args() 合并进最终配置对象。

python/finssim_cli/src/finssim_cli/main.py
python/finssim_marl/scripts/train.py

11. 训练真正使用配置的几个关键点

  1. setup_run() 根据 config_name 和 exp_name 确定 run 名称与输出目录。
  2. resolve_output_paths() 把日志、checkpoint、tensorboard 目录写回配置对象。
  3. base_config.create_mappo_config(config) 基于最终 TrainConfig 生成算法配置。
  4. base_config.create_algorithm(...) 创建算法实例。
  5. base_config.create_rollout_buffer(...) 创建 rollout buffer。

也就是说，base_config 不只是“一个字符串名字”，它在运行时会被解析成一个 带有工厂方法的配置对象，贯穿整个训练初始化阶段。

  |

13. 作为 instruction，排查配置读取问题时应按这个顺序看

  1. 先看顶层 YAML：base_config、experiment、unity、trainer.overrides。
  2. 再看 finssim_core/config_loader.py，确认 YAML 字段是否被正确接收。
  3. 再看 finssim_cli/main.py，确认这些字段被翻译成了哪些后端 CLI 参数。
  4. 再看 finssim_marl/scripts/train.py，确认哪些 CLI 参数会覆盖训练配置。
  5. 最后看 finssim_marl/training/config.py 和具体场景配置模块，确认 get_config() 和 create_train_config() 的实际行为。
